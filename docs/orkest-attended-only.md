# Attended-only: self-start inventory

`[features] attended_only = true` makes this installation do agent work only when a person (or an
Orkest-admitted run) asks. This page lists every path that could start agent work by itself, the
gate that stops it, and the test that fails if the gate is removed. It is the ORKEST-AGENCY 4.0
inventory; add a row when a new self-start path appears, and a test with it.

Path names are `file:symbol` under `packages/`. A "control" in a test name means the same scenario
on an ordinary installation, proving the test would notice the path running.

## Native tool approval (ORKEST-AGENCY 4.2)

A native agent's action outside its permission mode is put to the person as a question
(`UserInputModule.askForNativeToolPermission`). These rules keep that question from becoming a
self-start or a stale permission:

| Rule                                                                                                                                         | Where                                                                                                                                     | Test                                                                                                                         |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| The question expires (default 10 minutes, `ORKEST_NATIVE_QUESTION_EXPIRY_SECONDS`); expiry is a denial and a late answer is refused as stale | `sources/userInput/UserInputModule.ts:askForNativeToolPermission`, `:answer`; `sources/config/ConfigModule.ts:nativeToolQuestionExpiryMs` | `tests/userInput/NativeToolQuestionExpiry.test.ts`                                                                           |
| Questions an earlier process left pending are withdrawn at startup                                                                           | `sources/userInput/UserInputModule.ts:#withdrawStaleNativeToolQuestions`                                                                  | `tests/userInput/NativeToolQuestionExpiry.test.ts`: "withdraws them at startup ..."                                          |
| Who answered is recorded (`answeredBy`, team mode only)                                                                                      | `sources/api/ApiModule.ts` question answer route                                                                                          | `tests/userInput/NativeToolQuestionExpiry.test.ts`: "records the authenticated principal ..."                                |
| A bridged Happy tool that Happy refuses in the current mode is refused without a question                                                    | `happy-providers/sources/protocol/acp/AcpSession.ts:#happyRefuses`, tools tagged with `refusedInModes`                                    | `happy-providers/tests/protocol/acp/acpSession.test.ts` "bridged Happy tools"; `tests/artifacts/ArtifactBridgeModes.test.ts` |

## Orkest base release `0.0.67-orkest.1`

`packages/happy-agent-base` is frozen (AGENTS.md, "happy-agent-base is frozen": no change without
direct human input in the current task). The operator gave that input on 2026-11-12, relayed by the
Orkest parent session: "Yes, take 3cd056c (Recommended)", covering the restart change on
`orkest/attended-restart-base` and the base release it needs.

- **What it is.** `@slopus/happy-agent-base@0.0.67` from npm plus 3cd056c and nothing else. The
  unpatched source builds byte-identical to the published 0.0.67 `dist` (source maps aside), and the
  release tarball differs from it only in `AgentBase`, `AgentSystemLocal` (`.js`, `.d.ts`) and the
  version in `package.json`.
- **Where it lives.** `vendor/slopus-happy-agent-base-0.0.67-orkest.1.tgz` in this fork, sha256
  `5416d9f91994f8cd4b3937d6440eed89dc232f04006bc7acd45ac4c818dfcdee`. The `@slopus` npm scope is not
  ours, and AGENTS.md forbids publishing from local npm credentials, so nothing is published.
- **How it is consumed.** Every declarer (`happy-agent`, `happy-agent-modules`, `happy-agent-gym`)
  pins the same tarball (`file:../../vendor/...`), never `workspace:*`, so pnpm resolves one copy.
  No npm package depends on the base. The `happy-agent-modules` peer range also accepts the release.
- **Windows note.** On Windows every SQLite-backed base test can fail in teardown with `EBUSY` when
  the gym helper removes its temporary directory; the unmodified upstream
  `AgentPersistenceDrizzlePrefix.test.ts` fails the same way. With only that teardown error ignored,
  both restart tests pass.

## Gaps

- **Accepting a Spaces proposal** reaches `#startNewRows` only through `acceptProposal`, which needs
  a sidebar artifact and its document grammar. The gate is the first statement of `#startNewRows`;
  no test drives it yet.
- **Answering-principal binding.** Only team mode authenticates a person on the answer path
  (`teamUser(ctx)` in `ApiModule`). Standalone installations authenticate by bearer token, which
  names no person, so there is nothing to bind to. In team mode the answer records `answeredBy`, but
  an answer from a member other than the task's owner is not yet refused: that is a new `403` on
  `POST /v0/agents/:agentId/question/:questionId/answer`, which needs an `API.md` change.
